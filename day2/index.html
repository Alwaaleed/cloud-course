Foundations · version control

Git is save-points for your code, plus a shared home online

Git tracks every change you make and syncs it between computers through a site like GitHub. It matters here for one blunt reason: it is how code gets onto your server — and from this afternoon, what triggers a deployment.

cloneDownload a project from GitHub to your computer
addMark which changed files you want to save
commitSave those changes as a labelled snapshot
pushUpload your commits to GitHub

Four actions is enough

That is the whole of Git for today. Branches, pull requests and merges come on Day 5, when you have something worth branching.

You will click, not type

All four happen in VS Code's Source Control panel — no commands to memorise, no SSH keys to configure this morning.

Foundations · the one Git decision that already paid off

Fork first, then clone — why yesterday's choice matters today

Clone the starter directly the trap

Your copy stays pointed at our repository. You can commit locally all day, but the first time you push, GitHub refuses — you have no write access to someone else's repo.

You find out at the worst possible moment: at the end.

Fork, then clone your fork what you did

A fork is a full copy under your own account. Clone that, and every commit and push this week goes to a repo you own — including the one that triggers your deployments this afternoon.

On GitHub: Fork → Create fork, then copy your URL.
Already forked and cloned yesterday? You're set — move to the next slide. Haven't yet? In VS Code: Ctrl/Cmd + Shift + P → Git: Clone → paste your fork's URL — the one with your username in it, not ours.

Foundations · what Docker actually is

Docker packages your app so it runs the same everywhere

Yesterday virtual machine

Your ECS instance is a whole computer: its own kernel, its own operating system, a minute to boot.

Today container

Docker packages just your app and what it needs to run, and shares the host's operating system instead of bringing its own. It starts in seconds and runs the same way on any machine.

Docker the engine

Docker is the tool that builds, ships and runs containers — the six commands you are about to use all week.

One sentence worth remembering: a container is lighter because it never brings its own operating system. The next slide makes that difference visible.
Presenter: land this definition in words before the widget — "shares the host's OS, no guest OS" is the one fact the next slide's cost comparison depends on. Don't skip straight to the widget or the cost drop won't make sense.

Containers · two words people mix up

An image is the recipe; a container is the dish you cooked

Image the recipe

A frozen, read-only package of your app and everything it needs. It does not run. You build it once, push it to a registry, and pull it anywhere.

One image → many containers, on many machines.

Container the dish

A running instance of an image. Start it, stop it, throw it away, start another — the image it came from never changes.

docker run turns a recipe into a dish.
⚠️ "Image" now means two different things this week. Yesterday's image was the operating-system template you picked for your ECS instance. Today's image is a packaged application. Same word, different layer.
Presenter: this collision genuinely confuses people on day 2. Say it out loud once, then use "OS image" and "container image" for the rest of the week.

Foundations · naming an image, and where it lives

image:tag, and the registry it came from

Naming image:tag

An image's full name is image:tag. The tag picks a version or variant — leave it off and Docker assumes :latest.

nginx really means nginx:latest; node:22-alpine names the image and the exact variant.

Images live in a registry

A registry is a server that stores images for docker push and docker pull. Docker Hub is the default, and the one this course uses.

Docker Hub isn't the only one

Alibaba Cloud has its own Container Registry (ACR); GitHub has ghcr.io. Same idea, different host — the image name just gets a prefix.

ghcr.io/user/app instead of user/app.
In a moment, Hisham's task runs docker run … nginx. Docker won't find nginx:latest on the server, so it will pull it from Docker Hub automatically, first — before it ever starts the container.
Presenter: this slide pre-empts a question the Hisham task raises but never states — where does nginx actually come from? Land it here, before the task, so the pull-then-run behaviour isn't a mystery when they see it happen.

Containers · the commands you will use every day

Six commands run every container you meet this week

docker run <image>Start a container from an image
docker run -p 8080:80 …Map port 8080 on the host → port 80 in the container
docker run -v /host:/data …Mount a host folder — a volume — inside it
docker psList running containers
docker exec -it <name> shOpen a shell inside a running container
docker stop <name>Stop it

-d runs it detached

Without -d the container holds your terminal hostage. With it, it runs in the background and you get your prompt back.

exec is your window in

A container is not a black box. exec -it … sh drops you inside with the same ls and cd you learned yesterday.

Type exit to come back out.
Presenter: everything here is yesterday's shell knowledge pointed at a new target. Say that — it makes containers feel less like a new universe.

Containers · the flag everyone gets backwards

Send a request and watch exactly where it dies

Presenter: run it once mapped correctly, then flip to -p 80:8080 and send again — the packet crosses the wall and dies at a port nothing listens on. Land the rule out loud: host first, container second, and the container's port is decided by the image, not by you. Press "no -p" once too: a running container nobody can reach is the most common day-2 bug.

The Dockerfile · a recipe with two phases

Build the site with Node, then serve it with something tiny

Phase 1 — build node:22-alpine

Install dependencies, compile the React app, produce a folder of finished HTML, CSS and JavaScript in /app/dist.

Needs the whole Node toolchain. Needed once.

Phase 2 — serve caddy:2-alpine

Take those finished files and serve them over HTTPS. No Node, no compiler, no node_modules — a web server and a folder.

This is the only phase that ships to your server.
Two phases means FROM appears twice in one file. That is a multi-stage build — and the next slide shows what it saves.

Foundations · why this app insists on HTTPS

The camera will not open on a plain http:// address

The browser blocks it

Camera and microphone are privileged. Browsers hand them over only on a secure origin — HTTPS, or localhost. That is why the photo booth worked on your laptop.

Caddy gets the certificate

A tiny web server that fetches a real, trusted certificate automatically and renews it. No purchase, no manual setup — but it must be reachable to prove you own the name.

sslip.io gives you the name

You have an IP, not a domain. 47-253-1-100.sslip.io resolves straight back to 47.253.1.100 — free, instant, no DNS to configure.

Your IP, with dots turned into dashes.
⚠️ Open ports 80 and 443 in your instance's security group now (Alibaba console → your instance → Security Groups → inbound rules). Caddy needs 80 to prove ownership and 443 to serve. Do it now, understand it Thursday.
Presenter: be honest that the security group is a Day 3 topic they are taking on faith — the same deal as Git yesterday. Naming the debt keeps trust.

Docker Hub · somewhere both machines can reach

Your image needs an address of its own

Right now your image exists on exactly one machine: the laptop that built it. Your server cannot see it, and on Day 4 a Kubernetes cluster will not either. It needs to live somewhere both can pull from — a container registry.

Docker Hub is the default one

Free account, public images. Sign in from Docker Desktop and the CLI reuses that login — no docker login in the terminal.

Your image becomes <username>/cloud-explorer.
# on YOUR machine docker build \ --platform linux/amd64 \ -t <user>/cloud-explorer . docker push <user>/cloud-explorer
--platform linux/amd64 matters on an Apple Silicon Mac: your laptop builds ARM images by default and your server is x86. Skip it and the container refuses to start with an exec-format error.
Presenter: the platform flag saves the M-series half of the room twenty minutes of confusion. Say it even if nobody asks.

By hand · the deploy that works

Pull it on the server, run it, and open the padlock

# on YOUR SERVER, over SSH docker pull <user>/cloud-explorer docker run -d -p 80:80 -p 443:443 \ -e SITE_ADDRESS=47-253-1-100.sslip.io \ # your IP, with dashes --name cloud-explorer <user>/cloud-explorer

Yesterday's environment variable, doing real work

-e SITE_ADDRESS=… sets an environment variable inside the container — exactly the concept from Day 1. Caddy reads it to know which hostname to request a certificate for.

Then open it

https://<ip-with-dashes>.sslip.io — your badge, a trusted padlock, and a working photo booth. That is your app on the internet. 🌍

Presenter: put one student's URL on the projector. Everyone else will race to get theirs up, and that race is the best part of the day.

CI/CD · what the robot needs to know

Six secrets, so none of it ever sits in your code

GitHub Actions is the robot

It runs steps you define whenever something happens — here, a push to main. The steps are the same commands you just ran by hand.

Secrets, not source

Your private key and registry token go in Settings → Secrets and variables → Actions, never in the repository. The workflow reads them as ${{ secrets.NAME }}.

DOCKERHUB_USERNAMEyour Docker Hub username
DOCKERHUB_TOKENDocker Hub → Account Settings → Security → New Access Token
SSH_HOSTyour server's public IP (the EIP)
SSH_USERroot, or your login user
SSH_KEYthe contents of your private .pem file
SITE_ADDRESSyour <ip-with-dashes>.sslip.io
Presenter: Docker Hub shows the access token exactly once — tell them to paste it into GitHub immediately. Half the support questions this afternoon are a lost token.

Task · complete the deploy pipeline

Five blanks turn seven manual steps into one git push

on: push: branches: [______] # which branch deploys? jobs: build-and-push: steps: - uses: docker/login-action@v4 with: username: ${{ secrets.DOCKERHUB_USERNAME }} password: ${{ secrets.______ }} # which secret? - uses: docker/build-push-action@v7 deploy: needs: ______ # wait for which job? steps: - uses: appleboy/ssh-action@v1 with: script: | docker rm -f cloud-explorer || true docker run -d --pull ______ -p 80:80 -p 443:443 \ -e SITE_ADDRESS=${{ secrets.______ }} \ --name cloud-explorer …/cloud-explorer:latest
Presenter: point at --pull always and connect it straight back to the widget — this single word is the fix for the failure they just caused by hand.
