Foundations · the one-sentence definition

The cloud is renting someone else's computers, by the hour

That is genuinely it. The cloud is not magic and it is not one place — it is giant buildings full of computers owned by a provider, and you rent slices of them through a website called the console.

You can give the slice back the moment you are done, and stop paying for it. This week your provider is Alibaba Cloud.

A data centre — the building your "cloud" server is physically standing in.
Presenter: land "someone else's computer" hard. The single most common beginner belief to break is that the cloud is a different kind of computing rather than a different kind of renting.

Why rent · the trade you are making

Why anyone would rent instead of just buying a machine

Buying your own server

  • Thousands of riyals up front
  • Wait days for hardware to arrive
  • You fix it when it breaks
  • One machine, in one building

Renting from the cloud

  • A few halalas per hour, stop anytime
  • Ready in about a minute
  • The provider handles the hardware
  • Data centres all over the world
The thing you are really buying is speed of change — being wrong for an hour instead of being wrong for three years.
Presenter: ask the room which row matters most to a startup and which to a bank. Different answers are correct — that is the point.

The memory hook · if you forget everything else

Think of it as three ways to get a meal

IaaS you cook

The provider hands you raw ingredients — a bare virtual computer. You install everything and you are responsible for it. Most control, most work.

Concretely: the ECS instance you launch today.

PaaS half-prepared

A kitchen with the meal half made; you add your part. No hardware and no operating system to manage.

Concretely: a managed database, or object storage on Day 4.

SaaS cooked and served

The meal arrives finished. You log in and use it.

Concretely: Gmail, Netflix, Google Docs.
Infrastructure = building blocks · Platform = a ready service you build on · Software = the finished product. This week starts at IaaS and climbs toward PaaS.

Before you click launch · two decisions

Two settings you make today that you cannot redo later

1

The SSH key pair. This is your login credential. You download a .pem file once and you can never download it again. Lose it and the only fix is a new server. Guard it like a password — because it is one.

2

The security group. A firewall wrapped around your instance, deciding which ports the outside world may reach. The defaults are fine today; you will learn exactly what it does on Day 3.

Create the key pair first, before you start the instance wizard — otherwise you have to leave the page half-finished to go and make one.

Day 1 · Session 2 — operating your server

So far you have only clicked
at it. Now you drive it.

Real work on a server happens in a terminal, over a connection called SSH — and almost everything for the rest of the week happens there. This is the session where the cloud stops being a website and becomes a computer you operate.

First time really living in a terminal? That feeling is normal and it wears off today. You type the contents of the dark boxes and press Enter; lines starting with # are notes, not commands.
Presenter: name the discomfort out loud. Half the room has never used a shell and will otherwise assume everyone else has.

SSH · your secure line into the server

The key pair is one lock split into two halves

Your private key .pem

The file you downloaded and can never download again. It stays on your laptop. You never send it, paste it, or commit it.

The server's public key on the vm

The matching half, already installed on the server when you selected the key pair at launch.

They fit together proof

The server proves you hold the private half without you ever transmitting it. No password crosses the wire.

ssh -i ~/my-key.pem root@<your-EIP> -i ~/my-key.pem → identify me using this private key file root@<your-EIP> → log in as user root, at your public address
First connection asks whether to trust the server — type yes. When your prompt becomes root@iZ…:~# you are in, and that prompt is the server talking, not your laptop.
Presenter: the prompt change is the moment. Point at it on your own screen and say "everything I type now happens in a building I have never visited." Keep SSH shallow today — connect, key, done.

Moving around · the filesystem is one tree

Everything hangs off one root, and you are always standing somewhere

pwd where am i

Prints the directory you are standing in right now.

ls -l what is here

Lists the contents, with permissions, owner, size and date.

cd move

Changes directory. cd .. goes up one level.

mkdir make

Creates a directory.

$ pwd /root $ ls -l -rw-r--r-- 1 root root 220 Jul 5 10:00 notes.txt $ mkdir day1 && cd day1 $ pwd /root/day1
The tree starts at /. Everything else is somewhere below it.
Presenter: have everyone run pwd, ls -l, then mkdir day1 && cd day1 and pwd again. They keep that directory for tomorrow. Do not teach the whole filesystem hierarchy — they need four commands, not a tour.

Permissions · the ten characters in front of every file

Build the mode and watch SSH refuse your key

Presenter: it opens on 644 — the mode a freshly downloaded key actually has — and SSH is already refusing it. Ask the room why before you touch anything. Then click chmod 400 and watch it flip to accepted. Land: r=4, w=2, x=1, three groups, add them up. Finish on the ./report.sh line to set up the script task — a key must NOT be executable, a script must be.

Permissions · reading the ten characters

Three groups of three, and one letter in front

-rw-r--r-- 1 root root 220 Jul 5 10:00 notes.txt - rw- r-- r-- type owner group others

chmod 400 4,0,0

Owner read only, nobody else anything. This is what your SSH key needs — and SSH refuses a key that is more open than this.

chmod 755 7,5,5

Owner everything; group and others may read and run. The normal mode for a program.

chmod +x shortcut

Just add "executable", leaving the rest alone. What you use on a script.

That chmod 400 you ran this morning without knowing why? It means only I can read this, and nobody else can touch it.
Presenter: close the loop explicitly — they ran this blind in Session 1 and now it has a meaning. That callback is worth more than another example.

Combining commands · the real power of the shell

Watch seven lines go in and one come out

Presenter: in Pipe mode, switch the pattern between root, bash and nologin and let them watch different lines survive — cat never changes, only the filter does. Then add | wc -l and land that each stage only sees the previous stage's output. Switch to Redirect: press >> three times, then press > once. The room should gasp slightly. That is the lesson.

Pipes and redirection · the four symbols

One sends output to a command, the other sends it to a file

cat /etc/passwd | grep root # only lines containing "root" history | grep ssh # every ssh command you have run echo "hello cloud" > hello.txt # > write (OVERWRITES) echo "another line" >> hello.txt # >> append (adds to the end) sort < names.txt # < feed a file in as input

The pipe |

Plumbing. Data flows left → right, each command reshaping it. The command on the left never knows the one on the right exists.

> clobbers, >> appends. Mixing these up overwrites a file you meant to add to — the classic first-week mistake.
Presenter: make them run history | grep ssh on their own server. Seeing their own morning played back sells pipes better than any example you can invent.

Environment variables · named values the shell hands out

A value your shell passes to every program it starts

export NAME="Cloud Explorer" # set one echo "Hello, $NAME" # read it — $ pulls the value out echo $HOME # a built-in one env # list all of them

Why you will care tomorrow

The app you deploy this week reads its own web address out of a variable called SITE_ADDRESS. Configuration lives in the environment, not in the code — that is how the same image runs on your laptop and on your server.

Presenter: one minute. Set NAME, echo it, done. The payoff lands on Day 2 — do not try to teach twelve-factor config today.

Scripts · the commands you stop retyping

A script is just the commands you already type, saved in a file

#!/bin/bash # hello.sh NAME="$1" # $1 = the first argument echo "Hello, ${NAME:-world}!" # or "world" if none given echo "This server is: $(hostname)" $ chmod +x hello.sh $ ./hello.sh Salem Hello, Salem!

#!/bin/bash shebang

The first line says which interpreter runs this file.

$1 argument

The first thing you passed in — like a function parameter.

./ right here

"The file in this folder." Without it the shell searches its PATH instead and does not find you.

Presenter: connect chmod +x back to the permissions widget — without the x bit this file is text, not a program. That is why the widget showed Permission denied.

Task · Reem cannot remember what her server is doing

Fill the blanks so report.sh writes a tidy report

#!/bin/bash # report.sh - usage: ./report.sh "<your name>" export OWNER="____" # read the first argument into OWNER echo "=== Server report ===" ____ report.txt # start the file (overwrite) echo "Owner: $OWNER" ____ report.txt # append echo "Host: $(hostname)" >> report.txt echo "When: $( ____ )" >> report.txt # today's date and time echo "Uptime: $(uptime -p)" >> report.txt echo "Report saved for $OWNER!" cat report.txt | grep ____ # pull just the Owner line back out
Hints: start the file with a single >, then add every later line with >>. $(command) runs a command and drops its output straight into your text. Create it with nano report.sh; save with Ctrl+O, Enter, Ctrl+X.
Set it up verbally: Reem keeps losing track of which server she is logged into, so they write her a script that prints a report — practising variables, $1, redirection and a pipe in one go. Let them struggle for ten minutes before hinting. The single most common bug is using > on every line and ending up with a one-line file — exactly the lesson from the widget, so make them diagnose it themselves.
