Foundations · what actually breaks on one container

Why "one container on one server" doesn't survive contact with reality

A crash is a single point of failure

Your container dies — a bug, an out-of-memory kill, anything. Nothing restarts it. Your badge is down until you notice and SSH back in.

Scaling means you, by hand

App gets popular? You'd SSH in, run more containers yourself, and wire up a load balancer in front of them — every time traffic changes.

Kubernetes' one job

Watch your containers continuously and keep reality matching what you asked for — restart what dies, spread traffic across every healthy copy.

Everything from here is Kubernetes automating exactly this — nobody SSHes in at 2am to restart a crashed container again.
Presenter: keep this concrete — reuse their own badge as the running example. "If your one server's container died right now, who would notice first — you, or a user?"

Foundations · the idea under everything Kubernetes does

You declare desired state. Kubernetes enforces it, forever.

You don't tell Kubernetes how to run your app step by step. You describe the desired state — "I want 3 copies of this image, always" — and hand it over. Kubernetes runs a tight loop, forever: check reality, compare it to what you asked for, fix any difference.

while true: reality = what's actually running desired = what you asked for if reality != desired: fix it # start a Pod, or stop one

Like a thermostat

You set the target temperature once. The thermostat keeps checking and correcting — you never manually flip the heater on and off again.

This is "self-healing"

A crashed container isn't restarted by a script you wrote. It's this loop, noticing reality fell short and fixing it — usually before anyone notices.

Presenter: land "declare, don't script" as the one-sentence mental model before the four objects — everything after this is just naming the pieces this loop operates on.

Foundations · everything this week is built from exactly these

The four objects: Pod, Node, Deployment, Service

Pod smallest unit

One running copy of your container. Pods come and go — Kubernetes creates and destroys them constantly.

Node worker VM

A machine that runs Pods. A cluster has several — this is an ECS instance under the hood, same as your Day 1 server.

Deployment desired state

"Run N copies of this image, keep them healthy." Creates and replaces Pods for you. This is where scaling happens.

Service one address

One stable network address in front of your Pods, spreading traffic across them. Pods change constantly; the Service's address never does.

🧠 The mental model: Deployment = how many and which image · Pod = one running copy · Node = a machine to run copies on · Service = one front door to all of them.

Foundations · one cluster, walled off per student

Namespaces: the same trick your VPC pulled on Day 3

One shared cluster

The whole class deploys onto a single ACK cluster your instructor already provisioned. You are not creating a cluster today — it's already running.

Namespace your own area

A namespace walls off a slice of the cluster — the same way your VPC walled off your own network on Day 3. Every student creates their own, so nobody's Deployment collides with anyone else's.

ACK cluster (shared by the whole class) ├── namespace: sara (Sara's Pods live here) ├── namespace: turki (Turki's Pods live here) └── namespace: you ← you create this next session
